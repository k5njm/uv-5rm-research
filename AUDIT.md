# Project Audit & Roadmap (2026-11-06)

Static audit plus builds; **no radio was available**, so nothing here is hardware-verified.
Method: cloned all five upstream repos, decrypted factory/custom `.BF` files with an independent
decoder, built the core firmware, apps and host simulator (Rust 1.99.1), ran the simulator.

## Roadmap (suggested order)

1. **Recovery path:** there is no stock YP07 image, so recovery means (a) a SPI-flash backup *restore* tool, (b) keeping a known-good open-firmware `.BF` per release, proven to re-flash from bootloader mode, and (c) asking a YP07 owner (or the upstream author) to dump the stock firmware. Prove (b) on a sacrificial radio.
2. **Reproducibility:** record the toolchain per release; rebuild `.BF` and apps in CI and compare hashes.
3. **Existing features:** extend simulator coverage, add size-budget enforcement, resync with upstream `bf-5rh-firmware-open`.
4. **HAB apps:** move protocol code to host-testable crates with golden vectors; prove the BK4819 modem can do AFSK/4FSK before any RF code; user-configurable callsign.
5. **HIL:** sacrificial radio on a UART/CPS cable for flash/readback loops, then a second radio or SDR for over-the-air checks (dummy load, low power).

Tools: `firmware/tools/verify_release.py` (offline release gate), `.github/workflows/ci.yml`.
| 12 | `radio_read.py` (stock protocol, read-only) does **not** back up calibration (`0xF000-0xF260`), contrary to the earlier docs. The custom firmware has no CPS command that writes calibration (verified by reading `cps/mod.rs`: writes reach channels, VFO, settings, contacts, FM, logo, apps, sat data only), and `first_boot_format` does not erase it. `dump_nor.py` (read-only) can record it after the first flash; whether the stock protocol could read it before flashing is unknown. | Docs corrected; dump tool added (fake radio only) |
| 13 | `flash_bf.py` had no board gate. It now requires `--board` matching `--variant` (`firmware/variants.json`) before opening the port, and has `--check-only`. Mutation-tested: disabling the gate fails two tests. | Fixed, fake bootloader only |
| 14 | **Provenance of shipped binaries, measured** (`scripts/dev.sh provenance`): 9 of 11 shipped `.app` packages rebuild byte-for-byte from `firmware-source` (settings with 3 segments, text, search/QT, fm, spectrum, ...). Only `chanmgr.app` (1,220 code bytes differ) and the legacy `search.app` (443) do not, and the shipped core `.BF` differs from a build of its source. So the container and packer are not the cause of finding 6. **Experiments on the core `.BF` (2026-11-07):** all strings in the shipped image and in a rebuild are identical and the size is identical (61,352 bytes), so there are no text/UI changes; 181 byte ranges differ (15,730 bytes), with most 64-byte samples at the same offset and some shifted by 112-132 bytes, i.e. the same program with a different code layout. Ruled out: dependency versions (our `Cargo.lock` is identical to upstream's, and re-resolving dependencies is far worse: 56,406 bytes differ and the size changes); nearby compilers (1.99.1, the pinned one, is the closest at 15,730; 1.99.0 gives 23,233; 1.98 and older do not build the project). Not ruled out: a different rustc/LLVM build, different flags, or a small source difference that only changes layout. **The cause is still unproven**, but finding 18 sharpens it: the original author's environment reproduces the BK4819 build *exactly* on x86_64 Linux, so our compiler, lockfile and flags match theirs. Host architecture cannot explain the default image either (it is identical on arm64 and x86_64). That points at different source or build inputs for the shipped default `.BF` than what is committed. An earlier version of this note guessed "stale source" without evidence; this is better supported but still an inference. `mkapp.py` now records the entry address with the Thumb bit set (GNU `nm` form); this only affects package bytes, since the firmware ORs the bit in at load (`overlay.rs`). | Measured; cause of the `chanmgr`/`.BF` skew still unknown (see experiments) |
| 15 | **Simulator gaps closed while adding coverage** (each had made frames meaningless): `blit` was an empty stub (spectrum's waterfall vanished) and `draw_list` was a stub (chanmgr, FM and settings lists rendered black). Both now use the firmware's real behaviour (`ui/list.rs`). Scenarios now cover **all nine shipped apps** (text, foxhunt, bandsweep, rptfinder, searchqt, spectrum, fm, chanmgr, settings); every frame was reviewed by eye.
